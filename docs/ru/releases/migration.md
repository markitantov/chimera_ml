# Руководство по миграции

Это не дубликат журнала изменений, а список действий для подтверждённых изменений.

## Связывание конфигурации до 0.2.1

В версии 0.1.0 удалён `yaml_config`. Используйте текущие `ExperimentConfig`, разделы
YAML и функции построения CLI.

## Среда выполнения плагина до 0.2.1

BuildContext добавлен в 0.2.1. Функция построения, которой нужны метаданные предыдущего
компонента, должна объявить `context` и использовать `register`/`describe_context`,
а не изменять исходный YAML или глобальное состояние.

## Результат инференса в 0.2.4+

При `pipeline.parallel: true` параметр `--output/-o` больше не создаёт
`write_json_predictions_step` автоматически. Объявите шаг явно и задайте `after`.

## Обновления переборов

Текущие метаданные находятся в
`log_path/experiment_name/_sweeps/sweep_id`. Grid использует параметры или
испытания, Optuna — типизированные параметры и `sweep_target_callback`. См.
[Sweeps](../user-guide/sweeps.md) и канонический журнал изменений.


## Модели слияния только по признакам, выпущенные в 0.3.1

Текущие TFS, TFS-DCMMOE, RAAV и TOMAR — это новые архитектуры, работающие только
с признаками. Они принимают `input_dims`, `shared_dim` и `output_dim`, читают
предварительно вычисленные признаки из `Batch.inputs` и сами создают проекции и слои
предсказания. Это не обратно совместимое продолжение публичного API
`TOMARFusionModel(encoders=..., head=...)`: такого примера нет в выпущенной
реализации `main`, поэтому его нельзя использовать как исторический пример миграции.

Поля конструкторов описаны в руководствах конкретных моделей. RAAV также
требует `frame_modalities` и `context_modalities`; у TFS можно задать
`gate_hidden`, у TFS — `groups`, у TOMAR — `gate_hidden`.

## Намеренное удаление legacy fusion-моделей

В рамках рефакторинга намеренно удалены классы
`FeatureFusionModel`, `PredictionFusionModel`, `GatedFusionModel` и
`GatedPredictionFusionModel`, а также их registry keys
`feature_fusion_model`, `prediction_fusion_model`, `gated_fusion_model` и
`gated_prediction_fusion_model`. Прямой замены для этих классов
нет. Выберите одну из четырёх текущих моделей слияния только по признакам, если её
архитектура соответствует задаче, и явно перенесите контракт входов и выходов;
старые параметры конструктора и композиция подмоделей несовместимы.

Если модальностям нужны независимые дополнение последовательностей и временные маски, используйте
`multimodal_sequence_collate`. Во время CLI `train` и `eval` присутствующая
верхнеуровневая секция `collate:` разрешается через `build_collate()` и
передаётся в factory datamodule как `collate_fn`. Для такой интеграции пользовательский
DataModule должен явно объявить именованный параметр `collate_fn`. Если секции нет,
CLI не создаёт и не внедряет collate, сохраняя существующий DataModule по умолчанию,
включая legacy-поведение `MaskingCollate`.

Для удалённого устаревшего ключа реестра нет прямой замены.
